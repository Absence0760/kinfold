# Decision ledger

The record of judgment calls taken on the operator's behalf while building the roadmap: what was decided, why, and where it lives. Newest first. Each entry names the change that carries the call. Reverse any call you disagree with and the change with it — the ledger stays the place to read the calls without re-reading the code.

## 2026-11-03 — The audit runs its rules on the prerendered no-JS copy as well

- **The decision**: the screen-reader rule list and the reflow check became functions (`screenReaderProblems`, `overflowReports`), and a new `test.describe('with JavaScript blocked')` block runs both on `/` and `/transparency` with `javaScriptEnabled: false`.
- **Why the no-JS copy is a separate surface**: the public pages are prerendered, so a reader mode, a blocked tracker or a script-free browser receives the static adapter's HTML before any script runs, and screen readers work on that copy. An audit that only ever walked the hydrated document could pass while the version most accessibility tools actually hand a reader was broken.
- **Same rules, not a reduced list**: factoring the checks into functions is what keeps the two passes honest - a rule added once applies to both, so a future rule cannot quietly cover only the hydrated copy.
- **Why the client-side pages stay out**: sign-in and the error fallback are not prerendered, so with JavaScript blocked they carry no content for the rules to speak about; pinning an empty shell would accuse a page whose design is deliberate. They join the audit hydrated, and the member consoles once a configured stack exists.
- **Reversal:** if sign-in or the error fallback is ever prerendered, it joins this pass unchanged; if a surface grows JavaScript-required content that degrades on its own, that degradation gets its own pin here rather than a relaxed rule list.

## 2026-11-03 — Contrast is measured with WCAG's own ratio, on the colors the page paints

- **The decision**: the audit grew a contrast check per public surface (hydrated and the no-JS copy): every element's own text runs are measured with WCAG's ratio formula - 4.5:1, 3:1 for large print (18.67px, or 14px bold) - against the background stack the page actually paints: every opaque background-color from the page down to the element's own, composited in order, carrying each layer's opacity.
- **Why the ratio, not a palette check**: the design preview restyles surfaces (sticky nav blur, section alternates, cards), so a hardcoded palette would go stale and accuse nothing. Computing WCAG's ratio from `getComputedStyle` measures what the browser paints on every surface, today and after any restyle. The calculator's tokens already have their own unit-test contrast check (`SavingsCalculator.contrast.test.ts`); this rule extends the same promise to whole pages.
- **The vacuity trap, caught and kept**: the first pass of this rule carried a doubled-backslash rgba regex (`\\(` instead of `\(`), so no color ever parsed, every element `continue`d, and the rule passed on every page - a green test that measured nothing. The teeth proof is what caught it: forcing the threshold to 5:1 had to name real 4.95:1 text (the preview badge, the request-board status and kind labels), and it did. A contrast rule only ships with that proof in hand.
- **What it found**: nothing to fix. The site's tightest text sits at 4.95:1 (12px bold badges and status labels) - legal under WCAG's 4.5:1 - so the verdict comes from the standard, not from silence.
- **Reversal:** if a restyle ever drops text below 4.5:1 this rule reports it by element and ratio; if a page ever paints with CSS gradients, the compositing helper gains a gradient branch rather than the page being skipped.

## 2026-11-03 — Reflow gets teeth too: no public page may need a sideways scroll at 320 CSS px

- **The decision**: `a11y.spec.ts` grew a second check per public surface - resize the viewport to 320 CSS px and demand the document answer with no sideways scroll (`scrollWidth` at most the viewport), naming overflowing elements as culprits only when they can really cause a scroll.
- **Why 320 CSS px**: that is how WCAG states reflow - content stays readable at 200% zoom without a horizontal scroll, which is exactly the roadmap phrase "usable with a screen reader and large text from day one". The first half of that phrase had rules; the "large text" half had none, so a page built for wide screens would have passed the whole accessibility audit.
- **Why not browser zoom**: a 320px viewport asks the same layout question, and the audit already pins the viewport meta separately, so zooming would test the same thing through a noisier mechanism.
- **The name list only accuses real offenders**: an element inside a container that clips it (`overflow: hidden` or a scrollable shell) or inside a closed `<details>` menu (the mobile nav keeps its layout but shows nothing) cannot make the page scroll, so flagging one would blame a page a reader can already use. With the filter off, the audit itself names those elements as the culprit - proof the filter reads rather than silences.
- **Reversal:** if the member consoles gain their own error or wide-table pages once a configured stack joins the audit, the same rule applies per surface; if the site ever ships a legitimately scrollable widget (a comparison table inside a scrollable shell), the scrollWidth check is the one to keep and the name list to read - the page still answers with no document-level scroll.

## 2026-11-03 — A skip link is only honest if it is the page's first keyboard stop

- **The decision**: the accessibility audit grew an ordering rule - when a page offers a skip link, that link must be the first focusable element on the page; anything else that takes focus first is reported by name (tag and class).
- **Why ordering rather than existence**: the earlier rule checked that a skip link exists and that its target is real, and that rule would still pass a page whose menu comes first - a keyboard reader would Tab through every nav link before reaching the jump, which is the very burden the link promises to remove. The promise "usable with a screen reader and large text from day one" is about the ORDER of stops, not the presence of controls.
- **The site passed the first run**: the `(site)` layout renders the skip link inside `SiteNav` before the header links, so the rule found no slip. It is not vacuous: reading focus order is what the rule does, and pointing the comparison at any other position fails both public pages, naming the element that really takes focus first.
- **Pages without a skip link stay unjudged**: the sign-in page and the error page carry no repeated navigation, so there is nothing to skip and no order to demand.
- **Reversal:** if a page later grows a control that must precede the skip link (say a language switcher), the rule needs a small allow-list of element classes that may precede it - a two-line change in the audit, not a dropped rule.

## 2026-11-03 — The roadmap table checks its own step ids: unique, and never going back

- **The decision**: `check_docs_hygiene.mjs` now reads `docs/roadmap.md` as a plan, not just as markdown - every row whose first cell is a step id (`1a`, `2i`, ...) must be unique in the file, and the ids must never step backwards down the page.
- **Why the roadmap specifically**: it is the artifact this build works against, row by row. A duplicated step row makes it ambiguous which leg is actually landed - the reader who checks the first match reads a leg as done while the second, older-looking copy still reads open. A row filed out of stage order hides a leg from the reader who walks the table top to bottom, which is how every reviewer checks progress. Both slips are silent in a diff.
- **The rank is the stage number times a hundred plus the letter**: ordering is judged on the id itself, never on the row''s text, so rewording a step never moves its place.
- **Gate rows are not step rows**: Stage 0's rows have no id in their first cell, so this rule only speaks where the plan numbers its steps. The unlanded ones (1a, 2i, 3f) are still judged by their own blocked notes, not by this check.
- **Reversal:** if a stage ever numbers steps non-monotonically on purpose (say a 3z that must build before a 3d), the ordering check is the one to relax - drop the monotonic `if` and keep the uniqueness one, since a duplicate id is ambiguous under any numbering.

## 2026-11-03 — The ledger checks its own conventions: every entry dated, reversible, newest first

- **The decision**: `check_docs_hygiene.mjs` now reads `docs/ledger.md` as a ledger, not just as markdown - every `## ` entry must open with an ISO decision date, must contain a `**Reversal` bullet, and the dates must never step forward down the file.

Both slips are silent in review, and both were being checked by eye at every docs change.
- **Order is enforced on the dates alone, not on titles**: the file is a decision record, so "when did we decide this" is the sortable fact; a title that rewords a decision never moves its place.
- **Reversal:** if the ledger grows sections beyond decisions (say a "later corrections" block), the date rule moves from `docs/ledger.md` wholesale to a narrower heading match - the check is one `if` on the filename, so narrowing it is a local edit and nothing else changes.

## 2026-11-03 — Markdown conformance is a gate, not a convention checked by eye

- **The decision**: `scripts/check_docs_hygiene.mjs` (`pnpm test:docs`) now reads every tracked `.md` file and fails on a tab, a trailing space, three blank lines, a file not ended by exactly one newline, a table whose rows disagree on width, or a relative link whose file or heading anchor does not exist. It joined the root `test` chain, and it runs as its own CI job that is **not** gated on the code filter.
- **Why a script rather than review**: the repo's promise is that the docs stay readable wherever they render, and markdown defects are invisible in review - a table row with an extra cell reads as a mangled row on GitHub and as a syntax error on any other renderer. The convention was being enforced by hand at every docs edit, which is exactly the shape that drifts.
- **Why it runs on docs-only pushes**: the `changes` filter deliberately skips the heavy jobs on a markdown-only diff, because a docs push shouldn't pay for the stack and the browser. That skip is the one place markdown conformance is genuinely at stake - so this gate is the sole job that answers a docs push, and it costs a Node process with no install, no Docker, no Chromium. The single-emitter pattern in [README-ci-gate.md](../.github/workflows/README-ci-gate.md) stays intact: one added job, `ci-gate` still the only emitter, and the aggregator now refuses a skipped/failing docs job rather than tolerating it.
- **Untracked markdown is not judged**: the audit walks `git ls-files '*.md'`, so a `reviews/*.md` persona report (git-ignored by design) can never fail a push.
- **Reversal:** the rules are a list, not a dialect - dropping one (say, allowing three blanks for spacing) means deleting one check in the script and nothing else. If a docs job starts failing for reasons of its own, the gate can be made advisory by moving it out of `ci-gate`'s aggregation.

## 2026-11-02 — A family loan's schedule changes only by agreement ('loan_restructures')

- **Ladder step 3 for family loans** (design.md:137, "a new schedule both sides sign"): either side stages a restructure (smaller payments over a longer term, or a new start date) on their collecting loan; the *other* side signs it, and only on that signing do the unpaid installments re-spread — on the loan's payment day, like every other schedule (`set_loan_schedule`), so the loan keeps its payday rhythm.
- **A staged ask alone moves no money** — until both sides have signed, the schedule on the books is still the old one. One pending ask per loan; a second ask is refused while one waits.

- **One ask at a time**: while a restructure is un-applied a second ask is refused, and income schedules have nothing to reschedule (they are computed from income, not scheduled).
- **A paused loan can still ask to restructure** — the ladder goes pause, then restructure; pausing never blocks the bigger agreement step.

## 2026-11-02 — Payout reporting owns the outcome (`…210000_payout_reporting.sql`)

## 2026-11-01 — Step 1g: loan servicing (`…170000_loan_servicing.sql`)

- **Installments grew a `paid_on` date, written by a trigger rather than by callers.** `loan_installments` is written by several places (the schedule, the collector, the pause); a trigger keeps the date honest everywhere and the table check `(paid_on is null or paid_cents = amount_cents)` means a date can never exist on an installment that is still owed. `my_reliability` then counts payments made on or before the due date, which is what the name always promised. **Reversal:** rows paid before this column shipped carry no date and don't count as on time — the record understates rather than invents; if a backfill is ever wanted, it needs the partner's payment dates.

- **The default-plan trigger is a service-only view (`loan_default_due`), not an automatic status change.** Three or more unpaid installments more than 10 days past due, plus the borrower having used the whole pause allowance they agreed to in 12 months, and only while the loan is still collecting.
