# Build roadmap

What to build, in what order. Each stage ships something members can use, and the next stage starts only when the last one's gate is met. The product reasons behind the order are in [design.md](design.md#roadmap); the data model is in [backend.md](backend.md). Durations are planning estimates for a small team.

Open items outside the stages (CI gaps, backend edge cases, pending decisions) are tracked in [followups.md](followups.md). Whether each stage's product can work at all is in [feasibility.md](feasibility.md). The judgment calls taken while building — and how to reverse them — are in [ledger.md](ledger.md).

**Order rule:** build what moves no pooled money first. Every stage before Stage 2 can run with Kinfold holding nothing, so a mistake costs trust, not someone's savings.

## In every stage

- **Tests and docs ship with the code** (repo rule): pgTAP for every new rule in the database, Vitest and Deno tests for logic, Flutter tests for the app.
- **Security sweeps** before each stage's launch (`/audit/all`, plus `auth`, `gdpr` and `third-party-data-flows`), and a scoring bias audit every year.
- **Accessibility**: the member app is usable with a screen reader and large text from day one, because people post requests on their worst days. **Pinned 2026-11-03:** `e2e/a11y.spec.ts` walks the public surfaces like a screen reader does - language, viewport for large text, a heading outline with no skipped levels, `alt` on every image, named buttons and links, labelled form fields, one id per element, a skip link that lands somewhere, and a skip link that is the page's FIRST keyboard stop (an audit that only checks the link exists would still pass a page where the reader walks the whole menu first), and WCAG's reflow promise over all of it - no public page answers a 320-CSS-px viewport with a sideways scroll, which is what "large text from day one" commits to, and WCAG's contrast ratio over every element's own text (4.5:1, 3:1 for large print) against the colors the page paints, and the reduced-motion promise - under that browser setting no element may run an animation, no transition may glide on a movable property, no jump may glide, and WCAG 2.4.11: real Tab presses walk the page, every stop paints a focus ring, the walk closes its cycle without a keyboard trap (WCAG 2.1.2) and no positive tabindex rewires it (WCAG 2.4.3, both shapes: source order and the visual rect comparison), every visible hit target is at least 24 by 24 (WCAG 2.5.8), nothing interactive hides inside an aria-hidden subtree, every public page's own words name the design-preview status (a page that never says so reads as live operation), and two links announcing the same name resolve to one destination (WCAG 2.4.4) with one non-empty distinct <title> and a usable language tag per public surface, inline icon SVGs named or hidden (WCAG 2.4.2 and 1.1.1 and 1.2.1), and contrast also runs in the dark scheme (Playwright's colorScheme context), because the promise depends on what the page paints and the design ships two schemes. The audit runs twice per surface: on the hydrated page, and on the prerendered no-JS copy (`test.describe('with JavaScript blocked')`), because reader mode and script-free browsers get that HTML before any script runs (`landing.spec.ts` pins its copy offers no retry, because a 404 has nothing to retry): it found a real slip the first run: the transparency page's h1 shared the layout's `main` name, so `#main` was ambiguous and a keyboard reader tabbed the whole page; the member consoles join the audit when a stack-configured project runs them.
- **Local-first**: every new partner arrives with a local stand-in in the same change.
